# Security

What Bookflix does to protect readers and the catalog, what does not apply to this app and why, and what the owner has to set up outside the code.
Every measure below has a test or a pointer to the code that does it; the pointer after it says where.

## Applied

| Area | What is done | Where |
|---|---|---|
| Sign-in and sessions | Fortify email and password, email verification, two-factor and passkeys. The session is checked on the server by `auth`; sign-out and deactivation delete the session rows | `app/Providers/FortifyServiceProvider.php`, `config/fortify.php` |
| Every route is guarded | Each route carries `auth`, or is on a short, commented public list (landing, health check, covers, guest sign-in and reset, Livewire and Flux assets). A new route without `auth` fails the build | `tests/Feature/Security/RouteAuthCoverageTest.php` |
| Admin | Routes under `auth`, `verified` and `can:access-admin`; every admin page and action re-checks the gate; id properties are `#[Locked]` | `routes/admin.php`, `tests/Feature/Security/AdminRouteGuardTest.php`, `tests/Feature/Admin/AdminAccessTest.php` |
| Livewire updates | `verified`, `reader`, `onboarded` and `password.confirm` are replayed on every Livewire update, as the page route ran them | `app/Providers/AppServiceProvider.php`, `app/Http/Middleware/RequirePassword.php`, `tests/Feature/Security/LivewirePersistentMiddlewareTest.php` |
| Passwords | One shared rule set (`PasswordValidationRules`): in production at least 12 characters, mixed case, letters, numbers, symbols and not in a known leak (`uncompromised()`); in every environment at most 72 bytes, because bcrypt ignores the rest | `app/Concerns/PasswordValidationRules.php`, `app/Providers/AppServiceProvider.php`, `tests/Feature/Security/PasswordMaxBytesTest.php` |
| Rate limits | Sign-in, two-factor, passkeys, sign-up, password reset, password confirmation, search, the assistant, uploads, reports, reviews, verification resend and the reader and beacon routes | `app/Providers/FortifyServiceProvider.php`, `app/Providers/AppServiceProvider.php`, `tests/Feature/Security/AuthThrottleTest.php` |
| Form input | A list posted for a text field of an auth form is a validation error, not a crash. Every Livewire action and controller validates or re-checks the typed id it takes | `app/Http/Middleware/RejectNonStringAuthFields.php`, `tests/Feature/Security/AuthFieldTypeTest.php` |
| Request size | The JSON and beacon routes (reader progress, recommendation feedback, library add) refuse a body past 8 KB with 413. The legitimate maximum is about 2.5 KB. PHP's `post_max_size` and Livewire's own payload caps cover everything else | `app/Http/Middleware/LimitRequestBody.php`, `tests/Feature/Security/RequestBodyLimitTest.php` |
| Headers | `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` (needed for hotlink-protected covers), `Permissions-Policy` denying camera, microphone, geolocation, payment and USB, a nonce-based CSP, and HSTS for two years with `includeSubDomains; preload` on https outside the local environment | `app/Http/Middleware/SetSecurityHeaders.php`, `app/Http/Middleware/SetContentSecurityPolicy.php`, `tests/Feature/Http/SecurityHeadersTest.php` |
| Proxies and cookies | Trusted proxies come from the `TRUSTED_PROXIES` setting: unset trusts none, `*` trusts every caller (right on Vercel only), or a comma list; the client address, the https flag and every per-IP rate limit and security-log line follow it. The session cookie is `Secure` by default in production (`SESSION_SECURE_COOKIE` overrides) | `config/trustedproxy.php`, `config/session.php`, `tests/Feature/Security/TrustedProxiesTest.php`, `tests/Feature/Security/SessionCookieSecureTest.php` |
| Files | Reader files, comic pages and exports are served by signed, user-bound, throttled routes. The `local` disk is not served. Uploads are typed from their bytes, capped per format and by quota, and archives are checked against traversal, links and zip bombs. SVG is not a preview type | `routes/reader.php`, `config/filesystems.php`, `app/Reader/Archives/ZipGuard.php` |
| Output | Blade escapes. The only unescaped output is the server-made two-factor QR code. User text in reviews goes through `Markdown::safe` | `resources/views/pages/settings/⚡two-factor-setup-modal.blade.php` |
| Database | No raw SQL takes request input; every dynamic value is bound. Models list `$fillable`; none uses `$guarded = []` | checked in the Phase 1 inventory |
| Secrets and dependencies | Nothing secret in the repository or the JavaScript bundle (only `VITE_APP_NAME`). CI scans the full history with gitleaks, and runs `composer audit --locked` and `npm audit --omit=dev`: any advisory in a production dependency fails the `security` job (not a required check) | `.github/workflows/tests.yml` (job `security`) |
| Security log | Failed sign-ins, failed two-factor codes, 429s and 403s (Livewire updates included) are written to `storage/logs/security.log`, one line each: event, route name, method, IP, status, and the user id when known. A failed sign-in carries a 12-character SHA-256 prefix of the lower-cased email, never the email. Never a password, token, code, header or request body. Kept 30 days (`LOG_SECURITY_DAYS`). A throttled sign-in appears as `too_many_requests` on `login.store`: with the `login` limiter configured Fortify never fires its `Lockout` event, so the `lockout` line exists in the code but is not written in this setup. If the log cannot be written (permissions, full disk) the failure is reported on the default log and the request carries on unchanged, so a 403, a 429 or a wrong password is never turned into a 500 | `app/Support/SecurityLog.php`, `config/logging.php`, `bootstrap/app.php`, `tests/Feature/Security/SecurityLogTest.php` |

## Does not apply, and why

| Measure | Why not |
|---|---|
| Row-level security in the database | The app uses one database role and scopes every user-owned read and write in code (policies, `ownChats()`, `$user->collections()`, `visibleTo()`). RLS would need a per-request database role or session variable on every pooled connection. Database-level enforcement is an owner decision |
| A client-side login throttle | The server limiter already gives the "try again in N seconds" message; a client-only layer adds JavaScript and no protection |
| SECURITY DEFINER function hardening | The only database function is `immutable_unaccent`, a plain immutable SQL function |
| SSRF filtering of user URLs | No user-supplied URL is ever fetched. Provider and cover fetches only use `https` URLs on configured hosts, never follow redirects and cap size and type |
| CSV formula-injection guard | The app exports no CSV; the data export is JSON in a zip |
| Open-redirect protection | No request parameter feeds a redirect; the intended URL is kept in the server-side session |
| A `?next=` return URL | Not used |

## Owner-side controls (outside the code)

- **Host and proxy.** Set `TRUSTED_PROXIES=*` in the Vercel project's environment variables (its proxy is the only way to reach a function, and it overwrites `X-Forwarded-For`). With `*`, the client address is the leftmost `X-Forwarded-For` entry: whatever the client sent, unless the proxy replaces the header, which Vercel does. With a list of proxy addresses it is the rightmost entry that is not a listed proxy, which a client cannot forge; use a list on any host the app can also be reached on directly. A CDN in front of Vercel (for example Cloudflare's proxied mode) makes every visitor appear as the CDN's address, so all visitors share the per-IP rate limits. `X-Forwarded-Host` is deliberately not trusted, even from a trusted proxy: the reset and verification emails build their links from the request's host, so a client-supplied one would put an attacker's address in a real Bookflix email carrying the victim's token (covered by `TrustedProxiesTest`). For the same reason `trustHosts()` is not used, since it would also reject Vercel's preview hosts. Until `TRUSTED_PROXIES` is set, requests behind the proxy look like plain http: HSTS is not sent and per-IP rate limits and the security log see the proxy's address. `SESSION_SECURE_COOKIE=false` is for a production site still served over plain http.
- **APP_URL.** It must be the exact public https address (the custom domain, `https://`). The data-export download link is an absolute signed URL built from `APP_URL` in a queued notification and checked against the request's scheme and host when it is opened: an `http` address, or the `vercel.app` host when readers use the custom domain, answers 403.
- **HSTS preload.** The header carries `preload`. Submitting the domain at https://hstspreload.org is the owner's step, and it needs the apex domain and every subdomain on https permanently: removal from the browser lists takes months.
- **WAF or CAPTCHA.** None is built in. Add one at the host (or in front of sign-up and password reset) if abuse shows up in the security log.
- **Database role.** Run the app as a role that owns only its own schema, with no superuser rights, and keep the connection string server-side. Development uses the local `postgres` user.
- **Bucket privacy.** Keep reader files, comic pages and exports on a private disk or bucket and reach them only through the signed routes. Avatars and covers are public by design.
- **Dependency upgrades.** The audits run in CI in the `security` job, which is not a required check: a new advisory turns it red without blocking a merge. Keeping the lock files current is routine work for the owner. Development-only packages are not audited by `npm audit --omit=dev`; run a plain `npm audit` now and then.
- **Leaked-password check.** `uncompromised()` runs in production only, and sends a 5-character hash prefix of the password to the Have I Been Pwned range API (the password never leaves the server). If the service cannot be reached the framework reports the error to the application log and treats the password as not leaked, so sign-up and reset still succeed without the check; watch the application log for those errors and allow the outbound request at the host.
- **Log shipping.** `storage/logs/security.log` is a daily file kept 30 days. Ship it to wherever logs are watched if alerts on repeated 403s or 429s are wanted.
